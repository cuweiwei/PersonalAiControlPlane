## Current superseding separation decision (2026-08-31)

The shared AI Home Platform edge described in historical sections is retired. The active implementation is a Personal AI-owned private edge in the same non-root container: Tailscale HTTPS `:443` -> NAS loopback `127.0.0.1:9084` -> edge listener `:8081`. It owns Identity/Passkey, Control Web, Orchestrator/SSE, signed Worker HTTP/WebSocket, and the safe-method ContextHub Memory projection. ContextHub's public/Tailscale-facing `:8788` remains loopback-only; Personal AI reaches an additional Docker host-bridge-only ingress on `:18788`, without a shared Docker network. `/infrastructure` and `/api/portal/v1/infrastructure/*` are removed and return `404`. AI Home Platform, Traefik, OpenBao, Prometheus, Grafana, shared Docker networks, and the old `:9443` route are not runtime dependencies; their repository, data, Compose and immutable image remain independently recoverable. Infrastructure changes are performed by the owner/operator through the root-owned deployment gateway, never by the Orchestrator.

## 1. Design outcome

The first implementation is one TypeScript product with two deliverables:

```text
NAS release
└── pai-control-plane      one container and Node process
    ├── Identity           Passkey, sessions, forward-auth, action grants
    ├── Orchestrator       API, planning, durable execution, policy, scheduling,
    │                      compute routing, worker coordination, archive
    └── Control Web        built static management UI

Device release
└── pai-worker             macOS and Windows outbound execution runtime
```

`pai-control-plane` is a modular monolith. Modules interact through typed in-process ports and explicit authority APIs. Identity, Orchestrator, Conversation Archive, and Control Web intentionally share one process and container to minimize owner operations. Identity and Conversation Archive retain independent databases and ownership contracts, but process-level secret, restart, and compromise isolation is no longer claimed. The three module listeners remain inside the container, with the additional self-owned edge listener on `8081`; no external AI Home Platform aliases or shared network are required.

The design preserves these non-negotiable authority boundaries:

| Authority | System of record | Control Plane behavior |
| --- | --- | --- |
| Human identity | Identity module (`pai-identity-gateway` logical issuer) | Uses Passkey; never creates a parallel password or owner-managed service token |
| Goal and task execution | Orchestrator module (`pai-orchestrator` logical audience) | Only durable planner and task-state writer |
| Raw conversations | Conversation Archive | Stores normalized history and retention state |
| Semantic Memory | ContextHub | Compile/propose through its API; never copy accepted Memory into Orchestrator tables |
| Infrastructure operations | Owner/operator + root-owned deployment gateway | Execute validated deployment/rollback/status workflow; Orchestrator never calls Docker, NAS root, or the gateway |
| Production privilege | Root-owned NAS deployment gateway | Unchanged final deployment boundary |
| Provider credentials | OpenBao, root environment, or device OS vault | Expose only opaque capability handles |

### 2.1 Implementation baseline

| Area | v1 decision |
| --- | --- |
| Server and worker runtime | Node.js 22, TypeScript strict mode, ESM |
| Package topology | `pnpm` workspace with one lockfile and independently buildable apps |
| HTTP API | Fastify with generated OpenAPI and JSON Schema validation |
| Shared validation | JSON Schema 2020-12; TypeScript types generated from canonical schemas |
| NAS persistence | SQLite in WAL mode through a synchronous transaction-capable driver |
| Web portal | React, TypeScript, Vite; built static assets served by the unified Node runtime |
| Browser updates | Server-Sent Events for owner-visible state; REST remains authoritative |
| Worker transport | Authenticated outbound WebSocket; HTTPS long-poll fallback |
| IDs | UUIDv7 lowercase strings generated by the authority that owns the record |
| Timestamps | RFC 3339 UTC strings at API boundaries; integer Unix milliseconds in SQLite |
| Digests | SHA-256 over RFC 8785 canonical JSON or raw artifact bytes |
| Signatures | Ed25519; key IDs and public keys are versioned |
| Configuration | Git-owned, schema-validated YAML plus secret references from runtime environment |

Exact library versions are pinned when the workspace is bootstrapped. A library may be replaced without an architecture change if it preserves the schemas, transaction semantics, cryptographic formats, and public contracts in this document.

## 4. Runtime modules and ownership

### 4.1 Identity module

Owns:

- `identity.db` migrations and writes.
- WebAuthn registration/authentication challenges.
- Passkey users, credentials, recovery codes, sessions, CSRF, and step-up time.
- Forward-auth responses and verified internal identity headers.
- Service/device credential signing and action-grant signing.
- Public verification keys and key rotation metadata.

Does not own goals, approvals, policy decisions, provider credentials, or raw conversations.

### 4.2 Orchestrator module

The Orchestrator portion of the unified process contains:

- HTTP API and SSE projection.
- Goal admission, planning, estimates, and replanning.
- Task transition service and append-only task events.
- Policy and approval services.
- Scheduler, resource reservation, and quota manager.
- Worker coordinator and artifact ingestion.
- Compute-provider routing.
- Conversation Archive and connector coordination.
- Proactive trigger conversion.
- Credential-handle coordination.
- ContextHub, Hermes, and AIHomePlatform adapters.

Only one active Orchestrator instance opens the databases read/write. Startup takes an exclusive process lock. A second instance fails readiness rather than becoming a second scheduler.

### 4.3 Control Web module

The portal is a static single-page application. It uses only same-origin APIs, never receives provider secrets or signing keys, and treats SSE as an optimization. Refreshing a page reconstructs state from REST projections.

### 4.4 `pai-worker`

The worker owns device-local execution and enforcement:

- Device private key in Keychain or Windows Credential Manager.
- Outbound connection and reconnect state.
- Discovery and local health probes.
- Capability-specific sandbox adapters.
- Job lease, cancellation, checkpoint, and artifact upload state.
- Device-local credentials such as Codex ChatGPT login.

It does not plan, approve, expand a grant, or decide that an external side effect succeeded.

## 6. Goal, plan, and task model

### 6.1 Goal lifecycle

Goal status is a projection of durable goal events and child task states:

```text
PENDING -> PLANNING | CANCELLING | FAILED
PLANNING -> WAITING_APPROVAL | ACTIVE | CANCELLING | FAILED
WAITING_APPROVAL -> ACTIVE | REJECTED | CANCELLING | FAILED
ACTIVE -> VERIFYING | WAITING_APPROVAL | CANCELLING | FAILED
VERIFYING -> COMPLETED | ACTIVE | WAITING_APPROVAL | CANCELLING | FAILED
CANCELLING -> CANCELLED | FAILED
```

Rules:

- `POST /goals` commits `PENDING` before invoking Memory or a model.
- A goal has at most one active immutable plan revision; after activation it has exactly one until a replacement revision atomically supersedes it.
- `COMPLETED` requires acceptance-criteria verification, not merely all execution tasks returning success.
- `FAILED` stores a classified reason and recoverability; retry creates new task attempts, not a new goal.
- Cancellation never claims that already-committed external effects were rolled back.

### 6.2 Plan document

The canonical plan is immutable JSON conforming to `schemas/plan/v1/plan.schema.json`:

```json
{
  "schemaVersion": 1,
  "goalId": "019...",
  "revision": 1,
  "intent": "Add one supported source to Information Radar",
  "assumptions": [],
  "acceptanceCriteria": [
    {"id": "ac-1", "description": "Source ingests verified data", "verificationTaskId": "019..."}
  ],
  "context": {
    "memoryRequirement": "required",
    "scopes": ["project:information-radar"],
    "contextPackageRef": "sha256:..."
  },
  "estimate": {
    "durationMs": {"low": 7200000, "high": 14400000},
    "tokens": {"low": 80000, "high": 180000},
    "monetaryMicros": {"currency": "USD", "high": 0},
    "quotaImpact": "MAY_CROSS_WINDOW",
    "confidence": "MEDIUM",
    "basis": ["task-pattern:coding-integration", "repo-metadata"]
  },
  "risk": {
    "level": "MEDIUM",
    "hardStops": [],
    "externalEffects": ["git-push", "deployment-request"]
  },
  "tasks": [],
  "createdBy": {"kind": "planner", "modelRoute": "..."},
  "createdAt": "2026-08-28T00:00:00.000Z"
}
```

`plan_digest = sha256(RFC8785(canonical_plan_without_digest))`. A plan is rejected before activation when task IDs are duplicated, an edge references a missing task, the graph has a cycle, a verification task is absent, a capability is unknown, or a hard-stop action lacks a declared hard stop.

### 6.3 Task definition

Every plan task includes:

| Field | Meaning |
| --- | --- |
| `taskId`, `type`, `title` | Stable identity and human-readable purpose |
| `dependsOn[]` | Required predecessor task IDs |
| `required` | `true` for goal completion; `false` for exploratory work |
| `capabilityRequirements[]` | Version range, action, platform/resource constraints |
| `memoryRequirement` | `required`, `preferred`, or `none` |
| `sideEffectClass` | `NONE`, `READ_ONLY`, `IDEMPOTENT_MUTATION`, `NON_IDEMPOTENT_MUTATION` |
| `idempotencyKey` | Stable for one logical mutation |
| `budget` | Time, token, compute, monetary, and artifact limits |
| `sandbox` | Filesystem roots, network destinations, desktop mode |
| `checkpointPolicy` | Interval, safe points, portable fallback required |
| `retryPolicy` | Attempts, backoff, and retryable classes |
| `verification` | Assertions and evidence required for success |
| `rollback` | Supported action or explicit `none` with reason |

Exploratory tasks are not activated automatically when their incremental budget is outside the approved plan or they are unnecessary for acceptance criteria.

### 6.4 Task state machine

Canonical task states:

```text
PENDING
  -> ESTIMATING | CANCELLED | FAILED
ESTIMATING
  -> WAITING_APPROVAL | READY | FAILED | CANCELLED
WAITING_APPROVAL
  -> READY | CANCELLED | FAILED
READY
  -> DISPATCHED | WAITING_RESOURCE | WAITING_QUOTA | WAITING_AUTH | CANCELLED | FAILED
DISPATCHED
  -> RUNNING | RESUMING | READY | CANCELLED | FAILED
RESUMING
  -> RUNNING | CHECKPOINTED | WAITING_RESOURCE | WAITING_QUOTA | WAITING_AUTH
  -> WAITING_RECONCILIATION | FAILED | CANCELLED
RUNNING
  -> CHECKPOINTED | WAITING_RESOURCE | WAITING_QUOTA | WAITING_AUTH
  -> WAITING_RECONCILIATION | VERIFYING | FAILED | CANCELLED
CHECKPOINTED | WAITING_RESOURCE | WAITING_QUOTA | WAITING_AUTH
  -> READY | CANCELLED | FAILED
WAITING_RECONCILIATION
  -> READY | VERIFYING | FAILED | CANCELLED
VERIFYING
  -> COMPLETED | READY | FAILED | WAITING_APPROVAL
```

`RESUMING` is entered from `DISPATCHED` when the accepted attempt references a prior checkpoint. Terminal states are `COMPLETED`, `FAILED`, and `CANCELLED`.

Transition invariants:

1. The expected state and active plan revision must match.
2. The policy version and approval grant are re-evaluated before sensitive transitions.
3. Attempt-owned transitions require the current lease ID and fencing token.
4. Terminal success requires declared evidence references.
5. State row, event row, audit row when applicable, and outbox row commit in one transaction.
6. Invalid transitions return `409 STATE_CONFLICT` and do not append a transition event.

### 6.5 Transition transaction

```text
BEGIN IMMEDIATE
  read task and active plan
  compare expected state/revision
  verify lease and fencing token when attempt-owned
  evaluate invariant and policy guard
  update materialized task row with state_version + 1
  append task_event with previous/new state and redacted evidence
  append audit_event for control/security actions
  append outbox event with the same aggregate version
COMMIT
```

No network call occurs inside this transaction. Provider calls consume committed outbox work and report their result through a new transaction.

## 7. Persistence design

### 7.1 SQLite operating rules

Every authority database opens with:

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA synchronous = FULL;
PRAGMA busy_timeout = 5000;
PRAGMA trusted_schema = OFF;
```

Additional rules:

- One application writer serializes write transactions through an in-process queue.
- Read requests use short-lived read transactions and never hold a cursor across `await`.
- Schema migrations are monotonic, checksum-recorded, and applied before readiness.
- A migration failure leaves readiness false and never starts schedulers or connectors.
- Application code never edits historical migration files after release.
- Startup runs `foreign_key_check`, schema-version verification, and last audit-chain anchor verification.

### 7.5 Content-addressed artifacts

Logical layout:

```text
<artifact-root>/sha256/ab/cd/<64-hex-digest>
<artifact-root>/manifests/<artifact-id>.json
<artifact-root>/tmp/<upload-id>
```

Ingestion:

1. Stream to a newly created temporary file with a configured maximum size.
2. Calculate SHA-256 while writing.
3. Verify declared media type and optional expected digest.
4. Redact or reject artifact classes prohibited by policy.
5. `fsync` file and containing directory.
6. Atomically rename into the content-addressed path.
7. Commit the referencing database row.

Orphan temporary files are removed after a grace period. Content objects are deleted only when a mark phase finds no live reference in either authority's `artifact_references` table, the object is older than the safety grace period, and a retention/purge job explicitly authorizes deletion. The final sweep holds the Artifact Service's reference-registration mutex, rechecks both databases, then unlinks the object before releasing the mutex; this prevents a new reference from racing the delete. Cross-database reference scans are read-only reconciliation, and no table is used as another authority's write API.

## 8. Transactional outbox and background loops

Every durable background action is an outbox record. Topics include:

```text
goal.plan.requested
approval.notify
task.ready
job.dispatch.requested
task.verify.requested
memory.proposal.requested
notification.send
conversation.extract.requested
conversation.purge.requested
connector.run.requested
```

Dispatcher algorithm:

1. Select available undelivered rows ordered by creation time and priority.
2. Claim a small batch in a short transaction with `claimed_until`.
3. Perform the external call outside the transaction.
4. Record success by provider correlation ID, or classify failure and schedule backoff.
5. Reclaim after `claimed_until` when a process crashes.

Delivery is at least once. Consumers must deduplicate by `dedupe_key` or the downstream idempotency contract. After the retry ceiling, a row moves to a visible dead-letter state; it is not deleted.

Background loops are leader-local because only one Orchestrator is writable:

| Loop | Wake source | Safety behavior |
| --- | --- | --- |
| Planner | `goal.plan.requested` | one active planning lease per goal |
| Scheduler | state/outbox wake plus 2-second reconciliation tick | dispatch target p95 under 5 seconds |
| Lease reaper | 5-second tick | expires stale attempts; never blindly repeats uncertain mutation |
| Outbox dispatcher | commit signal plus 1-second tick | at-least-once with dedupe |
| Schedule evaluator | next-run timer plus 30-second reconciliation | stable firing key and misfire policy |
| Connector coordinator | configured due time | per-source lease and cursor |
| Retention/purge | hourly | forever policy is immutable to storage pressure |
| Quota probe | provider-specific due time | no work execution as a probe |

## 9. Owner API design

### 9.1 Common protocol

Base path is `/api/v1`. JSON is UTF-8 and unknown request fields are rejected on mutations.

Browser requests require:

- A valid Identity Gateway session.
- `Origin` matching the configured canonical origin.
- A double-submit CSRF header for every mutation.
- Fresh Passkey `auth_time` for step-up routes.

Workload requests require an automatically managed workload identity, an audience-bound action grant when performing a delegated action, and `Idempotency-Key` for every mutation. There is no general-purpose owner-managed API token.

The only unauthenticated mutation is the tailnet-only enrollment bootstrap request. It is rate-limited, accepts only a public key and bounded device summary, creates no trusted identity or capability, expires automatically, and cannot progress without owner Passkey approval of the exact fingerprint.

All successful resources include `id`, `createdAt`, `updatedAt`, and `version`. Mutations that edit an existing resource require `If-Match: "<version>"` and return `412 VERSION_CONFLICT` on stale writes.

List endpoints use cursor pagination:

```json
{
  "items": [],
  "nextCursor": null
}
```

Error envelope:

```json
{
  "error": {
    "code": "STATE_CONFLICT",
    "message": "Task is no longer in the expected state.",
    "requestId": "019...",
    "retryable": false,
    "details": {}
  }
}
```

`message` is safe for owner display. Stack traces, provider bodies, prompts, secret values, and raw external content are excluded.

## 10. Identity and action-grant design

### 10.1 Web session

Session cookie properties:

```text
HttpOnly
Secure
SameSite=Strict
Path=/
host-only cookie
```

The database stores only a SHA-256 hash of the random session identifier. Rotation occurs after login, recovery, and security-sensitive account changes. Logout and recovery revoke all selected sessions. Step-up compares the current time with server-side `auth_time`; client claims cannot refresh it.

Forward-auth behavior:

1. Private edge removes all incoming `X-PAI-*` identity headers.
2. Identity Gateway validates session, origin, route audience, and CSRF where applicable.
3. It emits verified owner ID, session ID, authentication time, and request ID to the upstream over the private internal route.
4. Upstreams reject direct requests missing the edge verification marker.

### 10.2 Worker enrollment

```mermaid
sequenceDiagram
  participant W as Worker
  participant O as Orchestrator
  participant I as Identity Gateway
  participant U as Owner

  W->>W: Generate Ed25519 key in OS vault
  W->>O: Enrollment request + public key + device summary
  O-->>U: Pending enrollment with fingerprint
  U->>I: Passkey step-up and approve exact fingerprint
  I->>I: Issue signed device credential
  I-->>W: Device ID + credential + trust anchors
  W->>O: Challenge proof with device key
  O->>I: Verify credential status
  O-->>W: Enrollment accepted; no capabilities granted
```

The enrollment challenge expires, is one-time, and is bound to the displayed public-key fingerprint. Re-enrollment creates a new identity; it does not silently replace an existing key.

Device credentials are short-lived and automatically renewed while the device identity is active. The private key never leaves the OS vault. Revocation closes connections and makes all later signatures invalid.

### 10.3 Action grant

Action grants use compact JWS with EdDSA. Required protected header and claims:

```json
{
  "header": {"alg": "EdDSA", "typ": "pai-action+jwt", "kid": "..."},
  "claims": {
    "iss": "pai-identity-gateway",
    "sub": "owner-or-workload-id",
    "aud": "pai-worker:019...",
    "jti": "019...",
    "iat": 1787875200, "nbf": 1787875200, "exp": 1787875500,
    "taskId": "019...",
    "attemptId": "019...",
    "planDigest": "sha256:...",
    "policyVersion": 12,
    "fencingToken": 7,
    "actions": ["codex.execute"],
    "resources": ["repo:information-radar"],
    "capabilityIds": ["019..."],
    "budget": {},
    "sandbox": {},
    "hardStopApprovalId": null
  }
}
```

Verification is fail-closed:

- Allow only the configured algorithm and an active/retiring `kid`.
- Require exact issuer and audience.
- Enforce `nbf`, `exp`, task/attempt, plan digest, policy version, and fencing token.
- Reject undeclared action, path root, destination, recipient, or budget.
- Consume `jti` when the adapter operation is one-time.
- Re-evaluate adapter-local hard stops even with a valid signature.

Default lifetime is five minutes and must not exceed the remaining approval-grant lifetime. A new action grant is minted for a retry; the approval grant itself is not exposed to a worker or provider.

Every audience persists a replay record keyed by `jti` or the operation idempotency key until at least `exp`. `identity.db.grant_nonces` covers grants consumed by the Identity Gateway itself; AIHomePlatform, Orchestrator, and workers enforce replay protection inside their own authority or durable local job store rather than sharing the Identity database.

### 10.4 Key rotation

- Signing keys have `PENDING`, `ACTIVE`, `RETIRING`, `RETIRED`, or `REVOKED` state.
- New verification material is published before activation.
- `RETIRING` keys verify existing unexpired grants but never sign new grants.
- Emergency revocation invalidates the key immediately and records an audit event.
- Rotation requires a restore-safe key handle; losing all active private key material is an authentication incident, not a reason to disable verification.

### 10.5 AIHomePlatform Passkey migration

The migration tool is schema-specific and must be completed only after inspecting the live source version. Its invariant workflow is:

1. Verify the configured canonical origin and RP ID exactly match the credentials being migrated.
2. Create and verify an AIHomePlatform authentication backup with rollback instructions.
3. Export users, passkey public material, counters/transports/backup flags, and hashed recovery data through a versioned offline manifest; never export a live session as reusable authority.
4. Enter a short authentication cutover window that prevents credential registration/change in the old authority.
5. Import into an empty or migration-target `identity.db` transaction and reconcile counts, stable credential IDs, public-key digests, counters, and recovery-code hash counts.
6. Invalidate old and imported browser sessions and require a fresh Passkey authentication.
7. Move one edge route at a time and verify login, CSRF, step-up, recovery, header stripping, and route isolation.
8. Keep the old authenticated route available for controlled rollback until the new boundary and backup/restore evidence are accepted.

Changing RP ID/origin, resetting signature counters without evidence, converting recovery hashes to plaintext, or keeping both authorities writable is a migration failure.

## 11. Policy and approval engine

### 11.1 Pure evaluation contract

```ts
type PolicyDecision = {
  outcome: "ALLOW" | "REQUIRE_APPROVAL" | "CHECKPOINT" | "DENY";
  policyVersion: number;
  matchedRuleIds: string[];
  requiredBounds?: ApprovalBounds;
  safeReasons: string[];
};
```

Inputs are immutable snapshots: actor, source, goal, active plan digest, task, intended action, capability descriptor, worker, sandbox, estimate, actual/reserved budget, recipients, credential class, data provenance, and current time. The evaluator performs no I/O and receives no secret value.

Evaluation order is fixed:

1. Invalid/missing evidence or stale policy -> `DENY` or `CHECKPOINT`.
2. Permanent prohibition, including autonomous privilege escalation -> `DENY` until explicit eligible approval flow exists.
3. Hard-stop match -> `REQUIRE_APPROVAL` with Passkey step-up.
4. Capability, worker, filesystem, network, recipient, and credential bounds.
5. Resource, quota, cost, duration, merge, and deployment thresholds.
6. Domain autonomy level.
7. Explicit allow rule; absence of allow -> `DENY`.

Hard stops are duplicated in the sensitive adapter. Policy configuration cannot remove the code-level minimum list; it may add stricter rules.

### 11.2 Approval grant containment

`contains(replan, grant)` is true only when all are true:

- Same goal and owner.
- New plan has no new hard-stop class.
- Required actions are subsets of allowed actions.
- Capability IDs, workers, filesystem roots, network destinations, and external recipients are subsets.
- Merge and deployment modes are no broader.
- High estimates plus actual/reserved usage remain within each maximum.
- Plan is before grant expiry and uses a policy version accepted by the grant.
- Reused completed task evidence still verifies against unchanged inputs.

Any unknown or incomparable dimension is treated as broader. The running task checkpoints at the next safe point, releases reservations, persists the proposed plan, and opens a new approval request.

### 11.3 Budget accounting

Each dimension tracks:

```text
approved maximum
actual committed usage
active reservations
remaining = maximum - actual - reservations
```

Reservation is required before dispatch. Providers report usage deltas with stable event IDs. Duplicates do not increment actuals. When usage telemetry is only estimated, policy uses the conservative high estimate. Exceeding a hard monetary maximum cancels further metered calls; it never auto-increases the grant.

### 11.4 Autonomy levels

| Level | Behavior |
| --- | --- |
| `NOTIFY` | Record evidence and notify; do not create an execution plan |
| `INVESTIGATE` | May run approved read-only investigation and report |
| `REPAIR_WITH_APPROVAL` | May investigate; repair plan requires approval |
| `AUTONOMOUS_WITHIN_GRANT` | May act only inside a current bounded grant |

User-submitted goals and proactive goals pass through the same evaluator. A proactive source never implies higher privilege.

## 12. Scheduler and resource reservation

### 12.1 Eligibility

A task is schedulable only when:

- State is `READY` and every required predecessor is `COMPLETED`.
- It belongs to the active plan revision.
- Cancellation is not requested.
- The policy decision is `ALLOW` under a current grant if one is needed.
- Credential handles are healthy or not required.
- The provider quota can be conservatively reserved.
- At least one online, trusted, non-draining worker advertises and has been granted all required capabilities.
- Worker protocol, sandbox, data locality, and action-grant versions are compatible.

### 12.2 Selection algorithm

Safety filters are never scores. Eligible tasks are ordered lexicographically by:

1. Earliest hard deadline, with no deadline last.
2. Owner priority: `URGENT`, `HIGH`, `NORMAL`, `LOW`.
3. Resume affinity for an already reserved provider/worktree.
4. Oldest `ready_at` to prevent starvation.

Candidate routes then pass a quality/capability floor. Remaining routes are ordered by policy using data locality, cost class, quota headroom, latency, energy preference, and worker load. The scheduler stores the selected route and an owner-safe explanation.

### 12.3 Atomic dispatch

```text
BEGIN IMMEDIATE
  re-read task eligibility and state version
  reserve worker/provider/quota rows
  increment task fencing counter
  create attempt in OFFERED state
  create lease with offer expiry
  transition READY -> DISPATCHED
  append job.dispatch.requested outbox row
COMMIT
```

The offer expires after 15 seconds by default. Acceptance must match attempt, lease, fencing token, capability descriptor hashes, and grant digest. A reject/timeout releases reservations and returns the task to `READY` with bounded jitter unless the reason maps to a waiting state.

### 12.4 Fairness and human Codex use

V1 permits at most one Orchestrator-owned Codex subscription execution at a time. A device-local `human_busy` signal or owner drain blocks new Codex offers. Because exact subscription capacity is not authoritative, the system does not claim a numeric human reserve. It preserves human priority through concurrency, drain, conservative quota observations, and no execution-as-probe behavior.

After an explicit limit error, the provider enters `EXHAUSTED`. Probe timing uses the best observed recovery time when confidence is sufficient; otherwise it starts at 30 minutes and backs off to two hours. A probe checks supported status or performs a zero-work capability check only. It never starts a billable task merely to learn whether quota reset.

## 13. Worker protocol

### 13.1 Connection and replay defense

Worker opens `wss://<configured-origin>/api/v1/worker/connect`. The host is deployment configuration, not hard-coded.

Handshake:

1. Worker sends credential ID, protocol range, random client nonce, timestamp, and device-key signature.
2. Server verifies identity status and timestamp skew, then returns a server nonce and connection ID.
3. Worker signs both nonces and connection ID.
4. Server marks the connection authenticated and associates one monotonic outbound/inbound sequence.

Every frame contains:

```json
{
  "protocolVersion": "1.0",
  "messageId": "019...",
  "connectionId": "019...",
  "sequence": 42,
  "workerId": "019...",
  "sentAt": "2026-08-28T00:00:00.000Z",
  "nonce": "base64url...",
  "type": "worker.heartbeat",
  "payload": {},
  "signature": "base64url..."
}
```

Signature covers canonical JSON excluding `signature`. Server rejects duplicate message IDs, non-increasing sequence, expired timestamp window, wrong connection, or invalid signature. Reconnect starts a new connection sequence; job-level event IDs retain deduplication across connections.

### 13.2 Heartbeat and capability manifest

Heartbeat interval is 30 seconds. Worker becomes `STALE` after 90 seconds and `OFFLINE` after the connection closes or the configured longer threshold. Heartbeat contains only bounded metrics and descriptors:

```json
{
  "health": "HEALTHY",
  "load": {"cpuPct": 18, "memoryFreeBytes": 123, "activeJobs": 0},
  "reservations": [],
  "capabilities": [
    {
      "kind": "codex.execute",
      "version": "1.0.0",
      "descriptorHash": "sha256:...",
      "health": "HEALTHY",
      "properties": {
        "loginMode": "chatgpt",
        "sandboxModes": ["workspace_write"],
        "maxConcurrency": 1
      }
    }
  ]
}
```

The descriptor schema allowlists properties per capability. Environment variables, paths outside declared roots, usernames, installed unrelated applications, tokens, and raw process lists are not reported.

### 13.3 Job offer

```json
{
  "type": "job.offer",
  "payload": {
    "jobId": "019...",
    "goalId": "019...",
    "taskId": "019...",
    "attemptId": "019...",
    "planDigest": "sha256:...",
    "capability": {"id": "019...", "descriptorHash": "sha256:..."},
    "lease": {"id": "019...", "fencingToken": 7, "expiresAt": "..."},
    "actionGrant": "<compact-jws>",
    "inputRef": "sha256:...",
    "sandbox": {},
    "budget": {},
    "checkpoint": null
  }
}
```

Worker acceptance is atomic locally:

- Verify message and action-grant signatures.
- Verify exact audience, worker/capability, attempt, plan, fencing, action, sandbox, and budget.
- Re-probe capability health and local credential mode.
- Acquire the local capability concurrency lock.
- Persist the accepted job envelope before replying `job.accept`.

Any mismatch returns a reasoned `job.reject` without executing.

### 13.4 Events, leases, and results

- Worker renews a running lease at least every one third of its duration.
- Server may extend only the current fencing token and valid grant bounds.
- `job.event` uses a stable `(attemptId, eventSequence)` and structured redacted payload.
- Progress text is capped and scrubbed; large logs are artifacts subject to policy.
- `job.result` includes outcome, external operation IDs, artifact hashes, usage, verification evidence, and the current fencing token.
- The server first persists the result as evidence, then transitions state in a separate guarded transaction.
- A stale result is retained as `STALE_RESULT_REJECTED` evidence and cannot complete a task.

### 13.5 Cancellation

`job.cancel` includes reason, requested time, and checkpoint deadline. The worker:

1. Stops starting new side effects.
2. Signals the adapter's cooperative cancellation mechanism.
3. Attempts a portable checkpoint at a safe point.
4. Reports completed/uncertain external effects.
5. Releases local locks after result acknowledgement or lease expiry.

Force-killing a capability process is permitted only when its adapter declares the resulting side-effect classification. Otherwise the task becomes `WAITING_RECONCILIATION`.

### 13.6 Long-poll fallback

Fallback endpoints use the same signed envelopes:

```text
POST /api/v1/worker/poll      receive offers/cancel messages, bounded wait
POST /api/v1/worker/events    upload heartbeat/events/results
```

Only one active poll per worker is allowed. WebSocket and long-poll connections for the same worker use a server-issued connection generation; the newer authenticated generation supersedes the older one.

## 14. Capability adapters and sandboxing

### 14.1 Adapter interface

```ts
interface CapabilityAdapter {
  discover(): Promise<CapabilityDescriptor | null>;
  probe(): Promise<CapabilityHealth>;
  validate(job: JobEnvelope, grant: VerifiedGrant): Promise<void>;
  execute(ctx: JobContext): AsyncIterable<JobEvent>;
  checkpoint(ctx: JobContext): Promise<CheckpointResult>;
  cancel(ctx: JobContext): Promise<CancelResult>;
  reconcile?(externalOperationId: string): Promise<ReconcileResult>;
}
```

Every adapter declares supported side-effect classes, sandbox modes, checkpoint semantics, external reconciliation support, and maximum concurrency.

### 14.2 Filesystem and shell

- Logical roots such as `repo:information-radar` resolve from worker-local configuration; NAS never sends an arbitrary host path as authority.
- Worker canonicalizes real paths after resolving symlinks and rejects traversal outside granted roots.
- New files inherit restrictive permissions.
- Shell uses named execution profiles with executable allowlists, environment allowlists, working-root restrictions, runtime/output caps, and network policy.
- Raw shell strings are data to a profile, not an implicit unrestricted capability.
- Privilege elevation commands are rejected by the adapter; approval does not make the worker type a password or bypass an OS prompt.

### 14.3 Codex adapter

Preflight must prove:

- Installed local Codex runtime is compatible.
- `forced_login_method` is `chatgpt`.
- Login status is ChatGPT subscription mode.
- `OPENAI_API_KEY` and other API-key fallback inputs are absent from the adapter environment.
- Target repository root is registered and the human working tree is not the execution directory.

Workspace flow:

```text
registered repository
  -> resolve approved base commit/ref
  -> create task-owned branch and isolated git worktree
  -> record worktree path and HEAD
  -> start/resume Codex thread with workspace_write
  -> checkpoint thread ID plus portable artifact
  -> run declared tests
  -> produce patch/commit/CI evidence according to grant
  -> retain or clean worktree according to terminal policy
```

The adapter never stages unrelated changes from the human checkout. `full_access`, direct production access, merge, push, release, deployment, and capability grant are separate declared actions.

Checkpoint must include the HLD fields plus:

```yaml
repository:
  logicalId: information-radar
  remoteFingerprint: sha256:...
  baseCommit: <sha>
  branch: agent/task-<id>
  worktreeRef: <worker-local-opaque-ref>
codex:
  threadId: <opaque>
  model: <observed-model>
  lastEventCursor: <opaque>
usage:
  observations: []
reconciliation:
  commits: []
  pushes: []
  pullRequests: []
```

If thread resume fails, a new Codex execution receives the portable checkpoint and verified repository state. It must reconcile before changing files.

### 14.4 Local LLM adapter

Discovery is two-stage:

1. Detect a configured LM Studio/oMLX endpoint locally without exposing it to the tailnet.
2. Probe each model for context window, modalities, tool-calling shape, throughput, memory usage, health, and current load.

`coding_quality` and other quality labels come only from versioned benchmark suites. An advertised OpenAI-compatible endpoint is not assumed to support every OpenAI feature. Probe evidence has an expiry; stale capability data excludes the route when the required feature cannot be safely assumed.

### 14.5 Browser and Computer Use

Default browser/CUA mode creates a dedicated browser profile and, where the accepted adapter supports it, a dedicated OS account/desktop session. The job has no access to the owner's active session.

Shared mode requires all of:

- Goal explicitly requests the current screen.
- Grant has `desktopMode = SHARED` and exact worker ID.
- Owner-visible indicator is active before the first action.
- Time limit and emergency revoke path are present.
- Privilege prompts and credential/security changes still stop.

Until a machine-specific CUA ADR and live isolation test pass, that worker advertises no `cua.execute` capability.

### 14.6 Docker/build and wake

- Build jobs may use a worker-local daemon under a named profile.
- NAS Docker socket, host namespace, privileged container, and arbitrary NAS mounts are never capabilities.
- Wake is a NAS-side narrow adapter configured with an accepted device identifier and network path.
- A wake request is successful only after the intended worker produces a new valid signed heartbeat.
- Automatic sleep is disabled until the machine-specific adapter proves it will not interrupt human use, another reservation, OS maintenance, or an uncheckpointed job.

## 15. Planning and replanning

### 15.1 Admission and lightweight estimate

Planning has two bounded stages:

1. Admission estimate uses request type, repository metadata, declared scope, known capability availability, and historical task-pattern aggregates. It must not read the entire repository or perform a full implementation design.
2. Detailed planning occurs only after the admission path permits the planning budget. It receives a bounded ContextHub package and resource snapshot.

Estimator output records ranges, confidence, and basis. A point estimate without a range is invalid. The initial planning budget is separately capped so a planner cannot spend the task budget merely discovering the plan.

### 15.2 Planner input boundary

The planner receives:

```text
owner intent and explicit constraints
accepted policy projection
bounded Memory context package
registered repository/service metadata
current capability and provider projection
historical estimate aggregates
supported task/capability catalog
```

It does not receive raw credentials, unrestricted conversation history, unrelated filesystem content, or direct infrastructure tools.

External content carries provenance labels. Although full prompt-injection detection is backlog, the plan schema retains source references at every derived assumption and task input so future taint rules can operate without changing the DAG contract.

### 15.3 Plan validation and activation

Activation pipeline:

1. Validate plan schema and canonical digest.
2. Check DAG acyclicity and required acceptance verification.
3. Resolve logical capability types to known schema versions; discovery is not authorization.
4. Evaluate policy and calculate required approval bounds.
5. Persist immutable plan revision and task rows.
6. If approval is required, create the request and leave tasks `WAITING_APPROVAL`.
7. Otherwise move dependency-free tasks to `ESTIMATING` and leave dependency-blocked tasks `PENDING`.

Tasks move from `PENDING` to `ESTIMATING` only when their dependencies complete and the active plan still references them. Estimate/policy evaluation then moves them to `READY` or `WAITING_APPROVAL`.

### 15.4 Replanning

Workers and adapters can emit `discovery.proposal` containing evidence and a suggested change. Only the planner produces a new plan revision.

Replan procedure:

1. Mark affected running tasks for a safe checkpoint when inputs or scope changed.
2. Capture completed task evidence and external operation IDs.
3. Generate a full replacement DAG; do not mutate the old plan JSON.
4. Classify old tasks as reusable, superseded, reconcile-required, or invalidated.
5. Evaluate approval-grant containment.
6. Atomically set the new active plan revision and materialize its tasks only after validation.
7. Reuse results only when input digest, capability contract, verification contract, and external state still match.

Old plan events and evidence remain queryable. A replan cannot erase an uncertain side effect.

## 16. AI Compute Broker

### 16.1 Provider contract

```ts
interface ComputeProvider {
  describe(): Promise<ProviderDescriptor>;
  probe(): Promise<ProviderHealth>;
  estimate(request: ComputeRequest): Promise<RouteEstimate>;
  reserve(request: ReservationRequest): Promise<ProviderReservation>;
  execute(reservation: ProviderReservation, input: ArtifactRef): AsyncIterable<ComputeEvent>;
  checkpoint(executionId: string): Promise<ProviderCheckpoint>;
  resume(checkpoint: ProviderCheckpoint): AsyncIterable<ComputeEvent>;
  cancel(executionId: string): Promise<CancelResult>;
}
```

Provider classes remain `deterministic`, `local-llm`, `codex-subscription`, and `cloud-llm-metered`. The broker never converts one class into another silently.

### 16.2 Route descriptor

Each candidate route includes:

| Field | Purpose |
| --- | --- |
| `providerId`, `providerClass`, `modelId` | Stable route identity |
| `capabilities` | Verified modalities, context, tools, coding/sandbox properties |
| `qualityEvidence` | Benchmark suite/version, score bands, expiry |
| `cost` | `ZERO_INCREMENTAL`, `SUBSCRIPTION_SHARED`, or metered estimate |
| `latency`, `throughput` | Observed range and timestamp |
| `quota` | Available/exhausted/unknown plus confidence |
| `worker/resource` | Data locality, load, memory, concurrency |
| `checkpoint` | Native, artifact-only, or unavailable |
| `credentialHandle` | Opaque reference and health only |

### 16.3 Routing algorithm

```text
candidates
  -> remove disabled provider classes
  -> remove missing required capability/modality/context/tool support
  -> remove routes below explicit quality floor
  -> remove unhealthy/stale/ungranted workers and credentials
  -> remove routes that cannot reserve the bounded budget
  -> apply data-locality and policy restrictions
  -> rank remaining routes by policy preference
  -> reserve chosen route before execution
```

Local-first is a ranking preference after the quality floor. A cheap route that cannot meet the verification contract is ineligible.

Route decision evidence includes candidates considered, rejection codes, selected route, estimate, policy version, and observation timestamps. It excludes prompts, raw content, and secret values.

### 16.4 Quota observations

Quota is an observation, not an invented exact balance:

```text
UNKNOWN -> AVAILABLE_ESTIMATE -> NEAR_LIMIT -> EXHAUSTED
EXHAUSTED -> RECOVERY_EXPECTED -> AVAILABLE_ESTIMATE
```

Sources have confidence:

1. Supported provider telemetry.
2. Structured SDK/runtime usage event.
3. Explicit provider limit error.
4. Historical inference.

An explicit limit error overrides an optimistic estimate. Recovery must be observed; the passage of an expected reset time only makes a conservative probe eligible.

### 16.5 Metered cloud providers

Metered providers are disabled unless both provider configuration and policy enable them. Execution requires:

- Healthy opaque credential handle.
- Currency and high monetary estimate.
- Reservation within an approved monetary maximum.
- Provider request idempotency/reconciliation where supported.
- Usage event capture.

When disabled or exhausted, the broker may choose another already-allowed provider class. It may not create or use an API key as fallback for `codex-subscription`.

## 17. Checkpoint and resume

### 17.1 Checkpoint levels

| Level | Requirement |
| --- | --- |
| Provider-native | Opaque thread/execution handle, treated as optimization |
| Portable | Versioned content-addressed artifact sufficient for a new adapter instance |
| External reconciliation | Operation IDs and evidence for effects outside the worker |

Every non-trivial task requires a portable checkpoint before it can enter `CHECKPOINTED` or `WAITING_QUOTA`. A provider-native handle without a portable fallback is insufficient.

### 17.2 Checkpoint manifest

The HLD manifest is extended without changing its required fields:

```yaml

planDigest: sha256:<hex>
```

The manifest is validated and its referenced artifact hashes are verified before resumption.

### 17.3 Resume reconciliation

Before execution resumes:

1. Confirm goal, task, active plan digest, and input digest.
2. Re-evaluate policy and remaining budget.
3. Reconcile all external operations marked pending or uncertain.
4. Verify local repository/workspace state when applicable.
5. Acquire a new lease with a higher fencing token.
6. Try native resume; fall back to portable reconstruction.
7. Append an event recording which path was used.

If checkpoint compatibility fails, the task does not restart from the beginning automatically. It requests replan or owner-visible recovery.

### 18.1 Normalized envelope

```json
{
  "schemaVersion": 1,
  "source": "hermes-telegram",
  "externalAccountHandle": "credential:telegram-owner",
  "conversation": {
    "externalId": "...",
    "title": null,

  },
  "message": {

    "revision": "1",
    "role": "user",
    "sentAt": "2026-08-28T00:00:00.000Z",
    "content": {"format": "text/plain", "text": "..."},
    "attachments": []
  },
  "provenance": {
    "connectorId": "hermes",
    "interface": "official-api",
    "observedAt": "..."
  },
  "checksum": "sha256:..."
}
```

Idempotency identity is `(source, account, external conversation, external message, revision)`. Same identity and checksum is a no-op; same identity and different checksum is a conflict unless the connector explicitly models edits as a new revision.

### 18.2 Retention calculation

Precedence, highest first:

1. Owner-approved conversation override.
2. Source-specific policy.
3. Scope-specific policy when exactly one most-specific rule matches.
4. Global default.

`null` means forever and stores `expires_at = NULL`. `0` means content becomes purge-eligible only after every linked active goal is terminal. A positive integer calculates expiry from message time, with ingestion time fallback recorded when source time is absent.

Changing policy is prospective. Retroactive expiry is a separate Passkey-step-up operation that previews affected counts/bytes before approval.

Storage pressure behavior:

- At warning threshold, alert and reduce optional connector concurrency.
- At critical threshold, stop optional large attachments and new nonessential connector ingestion.
- Preserve control events and owner goal admission where safe.
- Never reinterpret `NULL` expiry or delete content silently.

### 18.3 Export

Export is a durable task producing a manifest and content-addressed bundle. It records query, conversation/message IDs, checksums, provenance, retention metadata, export schema/version, and generation time. Export does not reset retention.

### 18.4 Verified deletion

```text
Passkey step-up request
  -> preview target/count/bytes and accepted Memory references
  -> create immutable tombstone
  -> block new reads/exports according to deletion state
  -> delete message bodies and attachment references
  -> garbage-collect unreferenced artifact bytes
  -> VACUUM/secure-deletion maintenance according to runbook
  -> write purge manifest and verify absence
  -> mark tombstone VERIFIED
```

The tombstone retains only target identifiers, reason class, actor, times, counts, and proof hashes. It does not retain deleted content. ContextHub Memory is not silently deleted; the preview identifies candidates whose archive source will be gone and requires an explicit Memory decision when policy demands it.

A tombstone records the covered external message IDs/revisions or cutoff cursor so connector replay cannot recreate purged content. Later messages outside the covered cutoff may be ingested unless the owner explicitly selected `blockFuture = true`; that choice is shown in the deletion preview and remains reversible without restoring already deleted bytes.

### 18.5 Extraction to ContextHub

Extraction task reads an explicit message range, records extractor/model version and input digest, and emits candidate facts/preferences/decisions/experiences with source references. It calls ContextHub candidate APIs idempotently. Accepted Memory IDs and review state are recorded in `extractions`; accepted rows remain ContextHub authority.

When `conflicts[]` is non-empty, the extraction remains unresolved and no conflicting claimant enters compiled context. Corrections use ContextHub successor semantics rather than update-in-place.

### 19.2 Directional sharing

- Work-to-personal ingestion may be scheduled when the work-device connector and policy allow it.
- Personal-to-work export requires content explicitly marked `work-shareable`, an allowed recipient/system, and outbound-sharing policy.
- `scope = work` is retrieval/provenance context, not sufficient outbound authorization.
- Corporate credentials remain resolved on the enrolled work device when required.

### 19.3 ContextHub adapter

Internal operations:

```text

proposeSuccessor(existingId, candidate, idempotencyKey)
recordContextOutcome(contextPackageId, outcome, idempotencyKey)
readChanges(cursor)
```

Rules:

- Deterministic service work uses REST; agent tool use may use MCP.
- Requests identify actual owner/tenant namespace plus conceptual scopes.
- Only accepted, active, authorized, non-conflicting Memory enters a context package.
- Package response is stored as a digest/reference, not copied into durable task events.
- `required` Memory failure moves the task to a waiting state; no hidden empty-context fallback.

The ContextHub scope migration is a separate repository change and ADR. This repository implements the target adapter but must keep it disabled against an incompatible ContextHub contract.

Compatibility requires a ContextHub feature response declaring the owner-domain plus conceptual-scope contract version. The migration in that repository must back up/export first, preserve item IDs where possible, revisions, source, authority, trust, reviews, successor/supersession links, claim keys, conflict behavior, audit evidence, and import provenance. Acceptance reconciles row counts and canonical checksums, rebuilds retrieval indexes, tests representative scope retrieval and same-`claim_key` conflict exclusion, then runs an isolated rollback. Existing personal/work namespaces are archived only after those gates pass; the Orchestrator never performs direct production SQL or uses a break-glass admin credential to bypass them.

The former `InfrastructureAdapter` and all Personal AI calls to AI Home Platform are retired. Personal AI does not proxy, schedule, or mutate infrastructure. AI Home Platform's repository and data remain recoverable but are not a runtime dependency.

## 20. Credential Broker

### 20.1 Handle model

A credential handle is a logical reference:

```text
credential://<storage-class>/<adapter>/<opaque-id>
```

Owner-visible state contains handle alias, purpose, storage class, adapter, scopes summary, health, expiry, and last verification. It never contains the resolved value.

Storage classes:

- `nas-vault`: OpenBao-managed runtime secret.
- `root-env`: root-controlled production environment reference.
- `device-vault`: macOS Keychain or Windows Credential Manager.
- `provider-session`: adapter-owned OAuth/session state.
- `codex-login`: local Codex/OS credential state.

### 20.2 Lease and injection

```text
task grant
  -> broker validates purpose, adapter, worker, policy, expiry
  -> narrow adapter resolves secret locally
  -> secret injected into one process/request scope
  -> adapter returns status/correlation only
  -> lease expires and temporary material is destroyed
```

The Orchestrator never asks an LLM to manipulate credential material. Environment injection uses an allowlist and child-process scope; it is not copied into checkpoints, events, artifacts, browser storage, or error messages.

### 20.3 Expiry and reauthorization

An `AUTH` error updates handle health, checkpoints the task when possible, releases resource reservations, transitions to `WAITING_AUTH`, and creates a notification. Reauthorization is a provider URL or device-local supported flow. Chat, API request bodies, and configuration forms do not accept pasted tokens.

## 22. Failure, retry, and reconciliation design

### 22.1 Retry classification

| Error class | Default action |
| --- | --- |
| `TRANSIENT` | Retry within declared attempts/backoff and current grant |
| `PERMANENT` | Fail task with evidence |
| `AUTH` | Checkpoint and `WAITING_AUTH` |
| `QUOTA` | Checkpoint and `WAITING_QUOTA` |
| `POLICY` | Deny or open approval; no retry loop |
| `CONFLICT` | Re-read/reconcile/replan |
| `UNCERTAIN_SIDE_EFFECT` | `WAITING_RECONCILIATION`; never blind retry |

Backoff is capped exponential with jitter. Retry counters are per logical task and per adapter operation; process restarts do not reset them.

### 22.2 Failure matrix

| Failure | Required behavior |
| --- | --- |
| Orchestrator crash before DB commit | No durable transition; caller retry uses idempotency record if present |
| Crash after commit before provider call | Outbox reclaims and delivers |
| Crash after provider effect before acknowledgement | Reconcile by external operation/idempotency ID |
| Worker disconnect during read-only work | Expire lease and retry on eligible worker |
| Worker disconnect during idempotent mutation | Reconcile, then retry if confirmed safe |
| Worker disconnect during non-idempotent mutation | Wait for reconciliation/owner action |
| Duplicate/stale worker result | Store rejected evidence; fencing prevents completion |
| ContextHub unavailable | Apply task `memoryRequirement`; never invent Memory success |
| Retired AI Home Platform | No Personal AI runtime dependency; owner/operator uses its independent recovery/deployment boundary |
| Identity module not ready | Existing non-expired worker execution may reach a safe checkpoint; no new grants or sensitive action |
| Artifact write/digest failure | Do not reference artifact or claim checkpoint |
| Disk warning | Alert/backpressure optional ingestion; preserve forever data |
| Disk critical | Stop large/optional writes before corrupting authorities; readiness becomes degraded/failing per threshold |
| Audit-chain mismatch | Fail sensitive writes and readiness; preserve evidence for incident handling |
| Clock skew beyond window | Reject signed message/grant and surface machine-time health |

### 22.3 External reconciliation record

Before or immediately after an external mutation begins, record:

```text
provider
operation kind
idempotency key
external operation ID when available
request digest
expected resource/version
started time
last observed state
reconciliation strategy
```

Completion requires the adapter to observe the expected external state, not merely a successful HTTP response.

## 23. Security design

### 23.1 Minimum enforcement

V1 enforces:

- Tailnet/private-edge entry.
- Passkey human root of trust, CSRF, and step-up.
- Automatically rotated workload identities.
- Short-lived action grants.
- Capability discovery/grant separation.
- Worker-local grant and sandbox checks.
- Credential isolation and redaction.
- No NAS root, Docker socket, unrestricted host mount, or interactive privilege escalation.
- Isolated CUA by default.
- Code-level hard stops at policy and adapter layers.
- Provenance fields for external content.

Prompt-injection detection remains backlog. Therefore broad autonomous action derived from untrusted external content must remain disabled until the backlog controls have an accepted design and evidence.

### 23.2 Trust-boundary validation

| Boundary | Validation |
| --- | --- |
| Browser -> edge | TLS/tailnet, origin, session, CSRF, route audience |
| Edge -> app | strip spoofed headers, private upstream, verification marker |
| Hermes/service -> API | workload identity, audience, idempotency, action grant when delegated |
| NAS -> worker | signed connection and messages, device status, exact capability grant |
| Worker -> adapter | action-grant bounds, local root/destination checks, credential purpose |
| Orchestrator -> ContextHub | typed API, owner domain/scope, idempotency, conflict fail-closed |
| Owner/operator -> gateway | repository-scoped Compose staging, validation, deployment, status, rollback |

### 23.3 Redaction

Redactor operates before serialization to logs, events, audit metadata, and error envelopes. It removes known secret fields, authorization headers, cookie values, private keys, recovery codes, signed grant bodies where not required, credential-looking environment values, and configured patterns.

Redaction tests use canary secrets and assert absence across HTTP responses, logs, task events, checkpoints, artifacts, metrics labels, and crash reports. Unknown raw provider output defaults to an access-controlled artifact or omission, not inline logging.

### 23.4 Audit chain

Audit hash input is canonical JSON of:

```text
sequence, event_id, timestamp, actor, action, target,
decision, policy_version, safe_metadata, previous_hash
```

Daily anchors are exported to the backup manifest. Verification checks sequence continuity, hash continuity, and anchor agreement. Audit events are append-only; corrections append a new event.

## 25. Backup, restore, and disaster recovery

### 25.1 Consistent backup

Backup coordinator creates independent authority snapshots:

1. Enter a brief snapshot barrier that drains the authority write queues and blocks artifact reference registration/deletion.
2. Ask each SQLite owner to create an online SQLite backup into a new timestamped directory.
3. Derive the referenced artifact set from those database snapshots and atomically write an artifact pin manifest that garbage collection honors.
4. Release the snapshot barrier, then verify `integrity_check`, `foreign_key_check`, schema version, and database checksum.
5. Copy and verify every pinned artifact object and build a content manifest.
6. Record Git commit/config digests, non-secret deployment coordinates, audit-chain anchors, and counts.
7. Encrypt and copy the set using the approved backup mechanism.
8. Write the final manifest only after every required object verifies, then retire the temporary artifact pin.

Copying a live `.db`, `-wal`, and `-shm` set directly is not an accepted backup method.

### 25.2 Backup manifest

```json
{
  "schemaVersion": 1,
  "backupId": "019...",
  "createdAt": "...",
  "productRelease": {"commit": "...", "imageDigests": []},
  "authorities": [
    {"name": "identity", "schemaVersion": 1, "sha256": "...", "size": 0},
    {"name": "orchestrator", "schemaVersion": 1, "sha256": "...", "size": 0},
    {"name": "conversation", "schemaVersion": 1, "sha256": "...", "size": 0}
  ],
  "artifacts": {"manifestSha256": "...", "count": 0, "bytes": 0},
  "auditAnchors": [],
  "configurationDigests": [],
  "encryption": {"method": "approved-external-workflow"}
}
```

Secret values and OpenBao data are not placed in this product manifest. The manifest references the independently protected OpenBao backup evidence.

### 25.3 Isolated restore drill

Restore drill uses an isolated path and no production route:

1. Verify manifest signatures/checksums before extraction.
2. Restore `identity.db`; invalidate all sessions in the restored copy.
3. Restore `orchestrator.db`; expire leases and mark running external mutations reconciliation-required.
4. Restore `conversation.db` and artifact objects.
5. Apply compatible forward migrations only when explicitly testing the target release.
6. Verify schemas, foreign keys, audit chains, task/event projections, checkpoint and artifact hashes, retention calculations, and sample exports.
7. Start services on isolated ports with external mutations disabled.
8. Produce a signed/hashed drill report and destroy the drill copy according to policy.

Restoring into live production is a separate destructive owner action and is never triggered by the drill.

### 25.4 Recovery objectives

- Daily consistent snapshot target gives RPO at most 24 hours.
- Orchestrator restart reconstructs schedulable state within five minutes at the HLD scale.
- All old leases expire on restore.
- Schedules follow their stored misfire policy.
- External operations remain uncertain until their owning adapter reconciles them.

- DAG with node state, dependencies, worker/provider, budget actuals, retries, and checkpoint status.
- Plan revision diff and approval containment reason.
- External operation and reconciliation state.
- Artifacts and safe logs.
- Cancel/retry actions with exact effect explanations.

The UI does not imply that health equals management, that a tombstone equals physical purge, or that deployment request acceptance equals live verification.

### 27.3 Approval experience

Approval view leads with:

- Intended outcome and plan diff.
- Duration/token/quota/monetary high estimates and confidence.
- Exact machines, capabilities, roots, network destinations, recipients.
- Merge/deployment permissions.
- Hard-stop reason and required authentication freshness.
- Expiry and what change would require reapproval.

Owner can narrow requested bounds but cannot broaden them from this screen. Reject and expiry are explicit terminal outcomes for that request; a planner may later propose a different plan.

### 27.4 Worker/capability experience

Discovered and granted state use separate controls and labels. Descriptor changes show a security-relevant diff. Wake shows request, network-adapter result, and signed-heartbeat result separately. Shared desktop state has a persistent visible indicator and revoke control.

### 27.5 Accessibility and mobile

- Keyboard navigation and visible focus for all controls.
- Text and status never rely on color alone.
- Tables collapse to labeled cards on narrow screens.
- Destructive and approval actions remain distinct and require clear confirmation/step-up.
- Polling/SSE reconnection never resets a form silently.

## 28. Deployment design

### 28.1 NAS stack

`compose.prod.yml` defines one pre-built immutable image and the approved project-scoped roots:

| Service | Network exposure | Persistent data |
| --- | --- | --- |
| `pai-control-plane` | private edge only through the existing Control Web, Identity, and Orchestrator aliases/listeners | separately mounted `identity.db` root plus `orchestrator.db`, `conversation.db`, and artifacts root |

The service uses no `build:`, privileged mode, host namespaces, Docker socket, devices, added capabilities, arbitrary host mounts, or root-owned production file writes. Its health check succeeds only when the static portal, Identity readiness, and Orchestrator readiness all succeed.

The stack has a unique Compose project name, independent image/release, persistent roots, backup set, rollback boundary, and exact NAS gateway allowlist ID. It does not require an AIHomePlatform manifest or runtime network.

### 28.2 Delivery chain

```text
source and docs
  -> local checks
  -> commit
  -> CI test/build
  -> one immutable Linux/amd64 image
  -> commit-bound release artifact and digests
  -> compose digest materialization
  -> staging upload
  -> root gateway validate
  -> deploy
  -> gateway status
  -> NAS loopback health
  -> tailnet health
  -> expected unauthenticated 401
  -> authenticated Passkey behavior
  -> backup and isolated restore evidence
  -> provider-specific evidence
```

The implementation must not deploy until the exact allowlist project exists. Deployment uses only the shared staging/validate/deploy/status workflow. Rollback restores the previous immutable Compose release; database downgrade support must be declared separately because image rollback alone cannot undo an incompatible migration.

### 28.3 Database-compatible release policy

Each release declares:

- Minimum and maximum readable schema versions.
- Forward migration set and checksums.
- Whether old application release can still read the migrated schema.
- Backup required before migration.
- Rollback procedure when schema is not backward compatible.

Destructive migrations use expand/migrate/contract across releases. The first release does not delete old columns in the same release that stops writing them.

## 29. Testing and verification

### 29.1 Test layers

| Layer | Required coverage |
| --- | --- |
| Schema/contract | Round-trip, unknown field, version negotiation, canonical digest/signature vectors |
| Unit | State transitions, DAG cycle, policy rules, containment, retention, route filtering, redaction |
| Property/model | Random transition sequences, budget monotonicity, hard-stop non-bypass, path containment |
| Database | Migrations, constraints, crash transactions, audit chain, online backup |
| Integration | API/auth/CSRF/step-up, outbox retry, worker lease/fencing, connector replay |
| End-to-end local | Goal -> approval -> worker -> checkpoint -> verify with fake external systems |
| Live/provider | Real Passkey, Hermes, Codex, local model, CUA, wake, ContextHub, AIHomePlatform |
| Production | Gateway/status/health/auth, backup, isolated restore, evidence coordinates |

### 29.2 Mandatory fault injection

Automated crash harness terminates the Orchestrator:

- Before and after every material state transition commit.
- After outbox claim and before/after provider call result recording.
- During worker offer, acceptance, lease renewal, checkpoint, and result.
- During connector page ingestion and cursor advancement.
- During artifact temp write and atomic rename.

Post-restart assertions prove no lost durable goal, no duplicate committed transition, no stale-fenced completion, and no blind repeat of an uncertain mutation.

### 29.3 Security tests

- WebAuthn RP/origin, challenge single use, replay, CSRF, session rotation, step-up expiry, recovery revocation.
- Spoofed edge identity header stripping and direct-upstream rejection.
- Device enrollment fingerprint binding, rotation, revocation, signed frame replay/skew/sequence.
- Action-grant wrong audience/action/resource/plan/fence/time/key and one-time nonce replay.
- Capability discovery without grant, descriptor broadening, symlink/path traversal, destination bypass.
- No autonomous hard-stop or privilege escalation under randomized policy inputs.
- Canary secret absence from every output surface.
- No `OPENAI_API_KEY` fallback for Codex subscription tests.

### 29.4 Acceptance scenarios

| Scenario | Acceptance evidence |
| --- | --- |
| Durable submission | API returns after commit; restart still shows goal and planning outbox |
| Approval containment | In-scope replan continues; broader root/recipient/budget checkpoints and re-asks |
| Worker loss | Stale fence rejected; safe retry or reconciliation state selected by effect class |
| Codex quota | Portable checkpoint, `WAITING_QUOTA`, lease release, later native/fallback resume |
| Human coexistence | Coding runs only in isolated worktree; active human checkout unchanged |
| Local routing | Quality-ineligible local model rejected even when cheaper |
| Context failure | Required Memory waits; preferred path records degraded context explicitly |
| Conversation forever | `NULL` expiry survives pressure; ingestion backpressure without deletion |
| Verified purge | Tombstone, byte removal, artifact GC, absence verification, safe audit proof |
| Deployment request | Orchestrator cannot bypass AIHomePlatform/gateway; full evidence chain distinguished |
| Credential expiry | `WAITING_AUTH`, owner reauthorization link, no token-paste path |
| Self-extension | Development, deployment, discovery, and grant remain separate decisions |

### 29.5 Evidence levels

Every subsystem has an evidence record:

```text
implemented_local
  -> ci_verified
  -> live_verified
  -> provider_verified
```

Evidence contains contract version, source commit, image digest when applicable, configuration digest, test/probe ID, observed time, target identity, result, and artifact hashes. Expired or mismatched evidence downgrades capability; it does not remain green indefinitely.

## 33. Detailed-design acceptance criteria

This design is ready for implementation when the owner accepts:

- TypeScript modular-monolith and shared-contract repository topology.
- Three independent SQLite authorities and a content-addressed artifact store.
- The exact task state machine, transition transaction, lease/fencing, outbox, and reconciliation model.
- Passkey sessions, automatically managed workload identities, and short-lived Ed25519 action grants.
- Pure fail-closed policy evaluation with adapter-level hard-stop duplication.
- Outbound signed worker protocol and discovery/grant separation.
- ChatGPT-only Codex adapter, isolated worktree, one Orchestrator execution at a time, and no API-key fallback.
- ContextHub and AIHomePlatform remaining external authorities behind typed adapters.
- Forever conversation retention with backpressure instead of silent deletion.
- Backup/restore, production gateway, live-health, auth, and provider evidence remaining separate gates.
- Items in section 31 remaining disabled until real owner/machine/provider evidence resolves them.
